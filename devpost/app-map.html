Crunch — App Map

What matters when crunch time hits. A local web app that reads your Moodle, strips out the noise (last year's modules, EC/extra-time duplicates, optional practice work), finds each assessment's weight in your module files, and shows what's left to do — month by month, ranked by priority.

The main pieces

app.pyFlask web app: the pages (dashboard, module, assessment, completed) and the buttons (tick, weight, set date).
moodle_client.pyTalks to Moodle with your token from .env: modules, quizzes, coursework, and whether you've done them.
tracker.pyPure logic: current modules, EC and optional detection, priority from weight, months, overdue, counts.
weight_finder.pyRuns in the background: reads module pages and PDFs, finds weights, adds exams/vivas/unreleased coursework.
storage.pyYour notes in data/tracker.json (weights, ticks, dates) and the offline copy of Moodle.
helper.pyThe free "Ask Crunch" answers — plain rules over your data, no AI service.

One action through the code: reloading the dashboard

The route (the three stops from the wrap-up)

1app.py → search def load_view

Every page starts here. It asks Moodle for a fresh snapshot, falls back to the cached copy (and the offline bar) if Moodle can't be reached, merges your notes, and kicks off the background weight finder when a module needs reading.

2moodle_client.py → search def call

Every question to Moodle goes through this one function. The key, the question and the answer format travel together:

query = {
    "wstoken": token,               # who I am
    "wsfunction": function,         # what I'm asking
    "moodlewsrestformat": "json",   # answer as JSON
    ...
}

Only this Python code ever sees the token — the browser talks to Flask, Flask talks to Moodle.

3moodle_client.py → search def _completed

For each opened assessment, asks Moodle mod_quiz_get_user_attempts or mod_assign_get_submission_status. A "yes" marks it completed, and tracker.build_view moves it out of the months and into Completed assessments.

To change this, start here

  • What counts as EC, optional, or a module → settings.json (keywords and the module-code pattern — no code changes needed).
  • Priority thresholds (≤10% Low, ≤50% Medium) → tracker.py, def priority.
  • Marks so far → grades fetched in moodle_client.py, def grades; combined with weights in tracker.py, def module_marks.
  • How weights are read from files → weight_finder.py, def find_weights and def match.
  • What the helper says → helper.py; its panel and greeting → templates/base.html (search Hi! Pick a question).
  • Look and feel → static/style.css (colours are variables at the top: --accent, --high, …).
  • Footer links → github_url / linkedin_url in settings.json.

A practice to reuse

Prove the risky unknown first, with real data. The spec flagged one thing everything depended on: would Moodle answer the way we assumed? Build step 1 was a small script, scripts/check_moodle.py, run against your real account before any dashboard existed. It exposed four surprises early — an SSL certificate problem, a single-sign-on token flow, non-module "in progress" courses, and several EC naming styles — each fixed in minutes and recorded under Revisions in devpost/checklist.md.

On your next project with an agent, ask: "What's the one thing that, if it doesn't work, the whole idea falls over?" — and have the agent build a tiny check for that first, before anything else.
